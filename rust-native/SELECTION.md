# Launch selection on the buy path

`src/selection.rs` is the go/no-go filter that belongs between "a pump.fun `create` was
reconstructed from shreds" and "sign and fire". It has no dependency on napi or solana-sdk, so
the same file drops straight into the shred proxy.

Measured on this machine against the real 67-creator table:

| path | cost |
| --- | --- |
| reject, creator not on the list | **1.5 ns** |
| accept, full plan built | **7.7 ns** |

That is one hash lookup plus a few `u128` multiplies. Nothing allocates, nothing locks, and the
table swap is wait-free (`arc-swap`), so a reload never stalls a decision.

## Wiring it in

At startup, once:

```rust
selection::load_from_file("creators.tsv")?;                       // fail fast on a bad table
selection::spawn_reloader("creators.tsv".into(), Duration::from_secs(30));
```

The reload matters: the wallet we copied rotates its whitelist on a cycle — split its window
into six blocks and deployers switch on and off wholesale — so the table is expected to change
under a running process.

In the shred handler, after decoding the `create` instruction:

```rust
match selection::decide_now(&creator, dev_buy_lamports, curve_quote_lamports) {
    Ok(plan) => fire_buy(mint, plan.token_amount, plan.max_sol_cost, plan.cu_price),
    Err(reason) => metrics.reject(reason),   // discriminant, nothing formatted on the hot path
}
```

`curve_quote_lamports` is the curve's quote reserve **including** the 30 SOL virtual offset —
i.e. `30 SOL + everything the dev and anyone ahead of us in the block has already put in`.
`decide` subtracts the offset itself to get the depth.

`plan.token_amount` goes in the pump `buy` instruction's `amount` field and `plan.max_sol_cost`
in its `max_sol_cost` field. That ordering is not cosmetic: pump's `buy` takes a **token
amount**, and decoding all 19,879 of the copied wallet's buys shows `amount == tokens received`
on every single one, with `max_sol_cost` carrying the actual position size in round 0.05 SOL
steps. Deriving the token amount at fire time from live curve state is strictly better than what
that wallet does — it pre-signs with durable nonces, so it has to guess the depth in advance and
eats a 6002 revert whenever it guesses low. That is 74% of its 19.5% failure rate.

## The table

`creators.tsv` at the repo root, regenerated by `analysis/make_creators_tsv.py`:

```
<creator base58>  <dev-buy floor SOL>  <budget SOL>  <cu price>  <min depth SOL>  <max depth SOL>
```

* **floor** — skip unless the deployer put in at least this much. On its own this rule accounts
  for 88% of the launches the copied wallet passes on.
* **budget** — becomes `max_sol_cost`. Three steps only (2.00 / 1.25 / 0.50): per-deployer edge
  repeats week to week at Spearman 0.26, so only the top quartile is worth up-sizing and
  fine-grading the middle fits noise.
* **cu price** — micro-lamports against a fixed 110,000 CU limit. Paid on reverts too.
* **depth band** — under 5 SOL of prior depth loses money, over 18 SOL is too late. The upper
  bound is enforced for free by `max_sol_cost`; the lower bound needs shred-level visibility of
  the create block, which this proxy has and a mempool-less RPC bot does not.

## Verifying a change

The module is self-contained, so it can be checked without building the whole napi crate
(which needs OpenSSL and is normally cross-built for Linux here):

```sh
mkdir -p /tmp/sel/src && cp rust-native/src/selection.rs /tmp/sel/src/lib.rs
printf '[package]\nname="sel"\nversion="0.1.0"\nedition="2021"\n\n[dependencies]\narc-swap="1"\n' > /tmp/sel/Cargo.toml
cd /tmp/sel && cargo test
```

The tests pin the curve maths against a real replayed create (a 1.843591186 SOL dev buy leaving
1,010,878,446 tokens), check that a budget round-trips through `cost_for_tokens` without
exceeding itself, and assert the rejection precedence.
